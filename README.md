**Summary of The Gaming Room Project**
For this project, I worked with The Gaming Room, a game development company that wanted to expand their Android-exclusive game, "Draw It or Lose It," into a cross-platform web application. The goal was to make the game more accessible to a wider audience by allowing it to run on multiple operating systems while maintaining the core gameplay experience.

**The main requirements were:**

The game needed to support multiple teams and players at the same time.
Each game, team, and player needed a unique name.
Only one instance of the game could be active at a time.
The new system had to be secure, scalable, and easy to maintain.

**What I Did Well in the Documentation
**I think one of the biggest strengths of my documentation was how structured and clear it was. I made sure to break down everything from platform comparisons to security considerations, so it’s easy to follow.

Another thing I did well was integrating software design principles into the project, like using the Singleton pattern to manage the game instance and object-oriented programming (OOP) techniques to structure the game, teams, and players. These decisions helped keep the game organized and efficient.

**How the Design Process Helped with Coding
**Writing out a detailed design document first made the coding process so much smoother. By mapping out how everything connects—like how teams and players interact with the game—I didn’t have to constantly go back and rework things.

It also helped me think ahead about potential issues, like making sure user authentication was secure and planning for cross-platform compatibility. Having a solid blueprint before jumping into the code saved a lot of time.

**One Thing I Would Improve
**If I had more time, I’d definitely add a system architecture diagram to show how everything connects visually. While I explained the logic behind how the game operates, a simple network diagram (showing how the client, server, and database interact) would make things even clearer for developers coming into the project.

**How I Considered the User’s Needs
**From the start, I knew that scalability and security were key to making this project successful. Players needed to be able to log in securely, game sessions had to be efficiently managed, and everything needed to run smoothly across different devices.

One example of this is how I implemented unique player and team names—without this, the game would get messy fast. I also recommended Linux servers since they’re cost-effective, secure, and reliable for handling online games.

Thinking about the user’s experience first helped shape a solid, realistic design that could actually work in the real world.

**My Approach to Software Design & Future Takeaways
**For this project, my approach was:

Start with clear requirements – making sure I understood what the client needed before diving in.
Use diagrams and design patterns – to keep everything organized and efficient.
Prioritize security and scalability – because a game like this needs to handle multiple players and teams without breaking.
In the future, I’d probably prototype earlier—even something as simple as a flowchart of how users interact with the system could make planning even easier.
